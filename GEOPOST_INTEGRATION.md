# Standalone GeoPost receiver and motion implementation
2026-11-26. Development foundation only. The existing Trusted card model uses title, slug, summary/content, heroImage, neighborhood/city/province, service_slug and published_at. This independent receiver uses stable multi-service IDs and a city/area ID; sender mapping is required. The exact existing sender endpoint/auth contract has not been verified; do not send to this receiver until an adapter and secrets are configured.

## Ingestion
POST /api/geoposts/ on the eventual DV demo/production host. Content-Type: application/json. Headers x-geopost-timestamp (Unix seconds), x-geopost-signature (sha256= plus hex HMAC-SHA256 of timestamp + "." + exact request body, using a dedicated >=32 character secret). Five minute clock tolerance. Body cap 32 KB. No credentials in source. Example (synthetic contract only, never publish):
```json
{"id":"job-example-001","revision":1,"status":"published","approved":true,"title":"Example contract title","summary":"Illustrative text only; replace with genuine owner-approved job description.","serviceIds":["general-towing"],"areaId":"black-diamond","completedOn":"2026-11-01","photo":{"url":"https://images.example.com/job.webp","alt":"Approved job photo description","publicApproved":true}}
```
Use the real stable job identifier, verified local area and completion date; revision increases on corrections. Same payload + revision is idempotent. Same revision with different content or stale revision is rejected. Withdraw with {"id":"job-example-001","revision":2,"status":"withdrawn"}. A record may target up to four services and one verified area. Only allowlisted service/area IDs and approved HTTPS image hosts accepted. Sender must strip EXIF, plates, faces where appropriate, exact addresses, phone numbers, customer identifiers and other private details before approval. Strict top-level fields, no injected HTML/scripts or incoming schema. Free text still requires human review; validation is not PII detection. No generated photos passed off as real jobs. Photos must have actual permission, not just a flag.
  
## Persistence and freshness
Dedicated Git branch geopost-data, data/geoposts.json, separate from main source. Receiver updates one JSON file via authenticated GitHub Contents API with blob SHA optimistic concurrency; retry conflicts up to three attempts. 500-record/850 KB compact JSON ceiling: archive/upgrade before limit. No ephemeral Vercel filesystem, no Supabase or Trusted Engine dependence. Read-only and write-capable fine-grained repo tokens stored server-side; scope to DVtowing only, rotate, never expose to browser. GitHub contents permission can modify other repo files, so use a separate data repository before production if stronger isolation is required. Configure Vercel to ignore geopost-data branch deployments or do not connect Git, so GeoPost writes don't cause builds. No hosted receiver, secrets, source integration or Vercel hookup currently active. Read cache nominal 300s; Next ISR may regenerate on subsequent traffic, not instant. No per-post deployment needed when configured. Monitor errors and storage capacity; move to isolated DB if volume warrants. For withdrawal urgency, add an authenticated cache purge and confirm live removal. Don't use personal customer information in Git history, which is retained even after withdrawal.
  
## Rendering / links
Homepage shows recent published records. Service pages filter by canonical service IDs, area pages by verified area. Cards are server rendered, link to related service/area URLs; same source record shared by filters, no duplicate standalone post pages. Empty feed renders nothing. Registry includes conditional routes; only candidate service routes are currently implemented. Before going live, connect approval registry to actual published routes and expand conditional pages, ensure no broken links, add canonical metadata/schema/sitemap and genuine content. Set GEO_APPROVED_SERVICES and GEO_APPROVED_AREAS to actually implemented/approved routes only. No date manipulation; freshness comes from genuine completed jobs. GBP posting is a separate approval workflow and not implemented.

## Sender utility
Set GEOPOST_RECEIVER_URL and GEOPOST_SECRET outside source control, then run `node scripts/send-geopost.mjs approved-job.json`. This signs the exact bytes and refuses redirects. The receiver additionally intersects configured service IDs with the presently implemented candidate routes, preventing broken related-service links. Extend candidate routes and reviewed content before expanding the allowlist. The data branch starts at the scaffold commit; source updates stay on main.
